== Deploying a 3-Tier Multi-Tier Application

Now that you are familiar with basic VM operations, it's time to build something real. For the **Red Hat Tech Day 2026**, we will deploy a complete 3-tier application architecture. This setup simulates a production environment where different components must communicate securely and reliably.

The architecture consists of:

1. **Database Tier (redis):** Provides high-performance in-memory data storage.
2. **Backend Tier (Python API):** Processing business logic and connecting to the DB.
3. **Frontend Tier (Nginx/html):** Serves the static content and UI.


=== Prepare Your Workspace

Open your terminal and ensure you are working in your assigned project.

. **Select your project namespace:**
+
[.lines_space]
[.console-input]
[source,bash, subs="+macros,+attributes"]
----
oc project {user}-application
----

. **Navigate to the lab repository:**
Make sure you are in the folder where the YAML files are located.
+
[.lines_space]
[.console-input]
[source,bash, subs="+macros,+attributes"]
----
cd ~/techday2026-virt/manifests
ls -la
----
+
[NOTE]
====
If you don't see the files or get a "No such file or directory" error, it means you need to clone the repository first. You can do so by running: 
`git clone https://github.com/manuvaldi/techday2026-virt.git ~/techday2026-virt`
====

=== Configure Application Parameters (ConfigMap)

Before launching the VMs, we need to provide them with the necessary configuration. We will use a **ConfigMap** to define where the Backend and Redis host are located. 

Copy and paste the following block into your terminal. Note that we are pointing the `REDIS_HOST` to the internal DNS name of our database service.

[.lines_space]
[.console-input]
[source,bash, subs="+macros,+attributes"]
----
cat <<EOF | oc apply -f -
kind: ConfigMap
apiVersion: v1
metadata:
  name: stock-parameters
  namespace: {user}-application
data:
  podman.env: |
    BACKEND_URL=http://backend:5000/data
    REDIS_HOST=database.{user}-application
EOF
----

=== Deploying the Virtual Machines

Now, let's deploy the three tiers in order. We'll start with the database so it's ready when the backend tries to connect.

. **Deploy the Database (Redis):**
+
[.lines_space]
[.console-input]
[source,bash, subs="+macros,+attributes"]
----
oc apply -f 03-vm-database.yaml -n {user}-application
----

. **Deploy the Backend (Python API):**
+
[.lines_space]
[.console-input]
[source,bash, subs="+macros,+attributes"]
----
oc apply -f 02-vm-backend.yaml -n {user}-application
----

. **Deploy the Frontend (Nginx/HTML):**
+
[.lines_space]
[.console-input]
[source,bash, subs="+macros,+attributes"]
----
oc apply -f 01-vm-frontend.yaml -n {user}-application
----

=== Explore Services and Routes

Once the VMs are in the **Running** state, OpenShift automatically manages their connectivity. 

. **Check the Services:**
+
[.lines_space]
[.console-input]
[source,bash, subs="+macros,+attributes"]
----
oc get svc -n {user}-application
----
+
Notice that each VM has a corresponding Service. This allows the Frontend VM to talk to the Backend VM using the hostname `backend`, and the Backend to talk to Redis using `database`.

. **Find your Route:**
The Frontend is exposed to the outside world through an OpenShift Route.
+
[.lines_space]
[.console-input]
[source,bash, subs="+macros,+attributes"]
----
oc get route -n {user}-application
----

=== Access the App

Copy the URL from the `HOST/PORT` column of the `oc get route` command and paste it into your browser.
